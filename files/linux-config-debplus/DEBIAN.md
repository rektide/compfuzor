# Building Debian kernel packages

This guide describes the recommended way to turn the configuration and source
hotfix in this repository into installable Debian packages. It targets the
local x86-64 workstation, Clang/LLVM, systemd-boot, and the crash-diagnostic
configuration preserved in `config-debian-plus.xz`.

## Current 7.3 target

The maintained entry point is [README.md](README.md). The target checked on
2026-10-01 is upstream commit `551c722f40809618230001baccf219193e22fc5a`
(2026-09-29), based on `v7.3-rc5` — not a final 7.3 release. The configuration
is migrated from the saved Debian-plus seed rather than a new Debian base;
the AMDGPU hotfix is ported to the per-power-source PPT-limit API.

Use the current `MAKE.sh` for the pinned baseline package recipe. This detailed
guide retains the **historical Linux 7.1 worked examples and 2026-08 host
measurements** below. Their filenames, package versions, tool availability,
storage headroom, and source line references are not current 7.3 instructions.
Adapt them to the actual release reported by `make kernelrelease`, and consult
the README for current normalization and patch-validation procedures.

Full configuration snapshots are now stored compressed. The historical plain
`config-debian-plus` paths below refer to the decompressed contents; use
`xz -dc config-debian-plus.xz` when preparing a current `.config`.

Nothing in this document runs automatically. Configuration, compilation,
packaging, installation, and boot selection are separate operator decisions.

## Recommendation

Use the kernel's upstream `bindeb-pkg` target with:

- the complete `config-debian-plus` configuration;
- the current AMDGPU source hotfix;
- `LLVM=1` on every Kbuild invocation;
- a unique `LOCALVERSION` for every boot-testable build;
- a matching, monotonically increasing `KDEB_PKGVERSION`;
- xz level 9 compression for retained binary package archives;
- the generated debug-symbol package retained for kdump analysis; and
- a one-shot systemd-boot selection for the first boot.

The conservative optimization baseline is Clang/LLVM with `-O2`, native CPU
tuning, and no LTO or profile-guided optimization. This is intentional. The
kernel supports more advanced LLVM optimization modes, but it still labels
ThinLTO and AutoFDO experimental, and their benefit depends on representative
measurement rather than the toolchain switch alone.

for tool in clang clang++ ld.lld llvm-ar llvm-nm llvm-objcopy llvm-objdump \

## Files and policy fragments

The configuration is intentionally split by responsibility:

| File | Purpose |
|---|---|
| `config-debian-plus` | Complete generated Clang/LLVM configuration; ready to copy to `.config` |
| `overrides.config` | Compiler-independent host, filesystem, networking, power, and crash policy |
| `overrides.llvm` | Clang/LLVM optimization and hardening choices |
| `overrides.gcc` | GCC/binutils fallback choices |
| `hotfixes/amdgpu-power.sh` | Checks or reapplies the local AMDGPU minimum-power-cap patch |

Kconfig derives compiler identity symbols such as `CONFIG_CC_IS_CLANG`,
`CONFIG_CLANG_VERSION`, and `CONFIG_LD_IS_LLD` from the tools used while running
Kconfig. Do not place those generated symbols in an override fragment.

The saved `config-debian-plus` was regenerated with `overrides.config`, then
`overrides.llvm`, and normalized with `LLVM=1`. The same process using
`overrides.gcc` without `LLVM=1` has also been validated.

## LLVM, Clang, and `LLVM=1`

Clang is the C compiler front end. LLVM is the larger toolchain project that
also provides the assembler, linker, archive tool, symbol tools, object-copy
tools, and related utilities.

Passing only `CC=clang` switches the C compiler while leaving most GNU binutils
in place. That mixed toolchain can be valid, but it is not this repository's
baseline.

Passing `LLVM=1` selects the coherent LLVM tool suite. In Linux 7.1 it expands
to the equivalent of:

```text
CC=clang
LD=ld.lld
AR=llvm-ar
NM=llvm-nm
STRIP=llvm-strip
OBJCOPY=llvm-objcopy
OBJDUMP=llvm-objdump
READELF=llvm-readelf
HOSTCC=clang
HOSTCXX=clang++
HOSTAR=llvm-ar
HOSTLD=ld.lld
```

This behavior is documented by the kernel in
[`Documentation/kbuild/llvm.rst`](/usr/local/src/linux/Documentation/kbuild/llvm.rst#L28-L77)
and in the published [Building Linux with Clang/LLVM](https://docs.kernel.org/kbuild/llvm.html)
guide.

Use the same `LLVM=` value for configuration, compilation, packaging, and any
later incremental build. Configuring with Clang and then invoking packaging
without `LLVM=1` can silently rerun Kconfig under GCC and alter compiler-gated
options.

`LLVM=1` is sufficient to select the complete LLVM toolchain. It does not
enable every optimization LLVM supports. Optimization policy remains in
Kconfig and, for profile-guided modes, additional build variables and profile
files.

## Optimization policy

The current baseline is deliberately conventional:

| Feature | Current policy | Reason |
|---|---|---|
| `CONFIG_CC_OPTIMIZE_FOR_PERFORMANCE=y` | Enabled | Kernel-standard `-O2`; default and well understood |
| `CONFIG_X86_NATIVE_CPU=y` | Enabled | Uses `-march=native` for this machine; reduces portability |
| `CONFIG_LTO_NONE=y` | Enabled | Avoids experimental and resource-heavy link-time modes |
| `CONFIG_LTO_CLANG_THIN` | Disabled | Supported on x86-64, but marked experimental; benchmark separately |
| `CONFIG_LTO_CLANG_FULL` | Disabled | Experimental, high memory use, long serial link stage |
| `CONFIG_AUTOFDO_CLANG` | Disabled | Requires a representative sampled workload profile to add value |
| `CONFIG_PROPELLER_CLANG` | Disabled | Standalone use is possible; the recommended flow adds another profile cycle over FDO |
| `CONFIG_CFI` | Disabled | kCFI is control-flow hardening with runtime checks, not a general speed optimization |

Linux 7.1 describes both Clang LTO modes as experimental and says LTO is very
resource-intensive. ThinLTO parallelizes more work and supports better
incremental builds than Full LTO, making it the only sensible LTO candidate for
a future experiment. See
[`arch/Kconfig`](/usr/local/src/linux/arch/Kconfig#L777-L864).

No-LTO is also a compatibility requirement for the canonical feature set.
Linux 7.1 disables `CONFIG_RUST` when BTF and LTO are both enabled because
pahole cannot safely exclude Rust compilation units from BTF after LTO merges
them. Rust is required for the DRM panic QR screen and is an explicit project
requirement; BTF is retained for advanced BPF introspection. Therefore the
canonical LLVM build keeps `CONFIG_LTO_NONE=y`.

AutoFDO and Propeller can improve real workloads, but they are feedback-driven
systems rather than free compiler flags. A useful AutoFDO profile must be made
from representative hardware samples. Propeller can run alone, but the kernel
strongly recommends applying it over AutoFDO, AutoFDO plus ThinLTO, or
instrumented FDO; in that recommended flow it adds a second profiling cycle.
Poor training data can optimize the kernel for the wrong workload. See the kernel's
[AutoFDO](https://docs.kernel.org/dev-tools/autofdo.html) and
[Propeller](https://docs.kernel.org/dev-tools/propeller.html) guides.

We have enough knowledge to choose the conservative baseline and construct
repeatable experimental variants. We do not yet have workload measurements that
justify enabling ThinLTO, AutoFDO, or Propeller in the canonical configuration.

Compiler choice also does not capture every runtime cost in the common config.
For example, the inherited Debian configuration enables UBSAN bounds and shift
checks, dynamic debug, ftrace, and full debug information. Those facilities can
affect build size or runtime overhead, but they are not LLVM-versus-GCC choices.
Reviewing them should be a separate measured configuration-policy change rather
than being hidden in a compiler fragment.

## Versioning

Give each installable test kernel a unique kernel release. The release becomes
part of the package name, `/boot` filenames, initramfs name, and
`/lib/modules/<release>`. Reusing a release overwrites the previous build and
makes rollback and symbol matching harder.

For an initial example:

```text
LOCALVERSION=-debplus.1
KDEB_PKGVERSION=7.1.0-1
```

For the next independently bootable build:

```text
LOCALVERSION=-debplus.2
KDEB_PKGVERSION=7.1.0-2
```

`LOCALVERSION` identifies the kernel ABI and boot artifact. `KDEB_PKGVERSION`
controls Debian package ordering. Increment both for a new kernel that should
coexist with its predecessor. Incrementing only `KDEB_PKGVERSION` is reasonable
for a packaging-only correction that intentionally replaces the same kernel
release.

This repository disables `CONFIG_LOCALVERSION_AUTO`. In that configuration, an
explicit `LOCALVERSION` suppresses the fallback SCM suffix, including the
current generic `-dirty` result. If `CONFIG_LOCALVERSION_AUTO=y`, Kbuild may
still append `-dirty` despite a command-line `LOCALVERSION`. Naming never makes
an uncommitted source tree reproducible; record or commit the actual changes.

## Baseline package build

### 1. Restore the configuration

```sh
cp /usr/local/src/linux-config-debplus/config-debian-plus \
  /usr/local/src/linux/.config
```

### 2. Check the source hotfix

The check is read-only:

```sh
/usr/local/src/linux-config-debplus/hotfixes/amdgpu-power.sh \
  --check /usr/local/src/linux
```

If it reports that the hotfix applies cleanly rather than already being
applied, apply it explicitly:

```sh
/usr/local/src/linux-config-debplus/hotfixes/amdgpu-power.sh \
  /usr/local/src/linux
```

### 3. Normalize and inspect the release

```sh
make -C /usr/local/src/linux \
  LLVM=1 LOCALVERSION=-debplus.1 olddefconfig

make -s -C /usr/local/src/linux \
  LLVM=1 LOCALVERSION=-debplus.1 kernelrelease
```

The example should report `7.1.0-debplus.1`. These commands update generated
configuration state but do not compile the kernel.

Before the long build, inspect the effective compiler and critical policy:

```sh
grep -E 'CONFIG_CC_VERSION_TEXT|CONFIG_CC_IS_CLANG|CONFIG_LD_IS_LLD|CONFIG_LTO_|CONFIG_X86_NATIVE_CPU' \
  /usr/local/src/linux/.config
```

### 4. Build binary Debian packages

Select high-compression xz archives for packages worth retaining. Level 9 is
deliberately aggressive but remains a standard dpkg-deb mode:

```sh
export DPKG_DEB_COMPRESSOR_TYPE=xz
export DPKG_DEB_COMPRESSOR_LEVEL=9
export DPKG_DEB_THREADS_MAX=16
```

Then build:

```sh
make -C /usr/local/src/linux -j16 \
  LLVM=1 \
  LOCALVERSION=-debplus.1 \
  KDEB_SOURCENAME=linux-debplus \
  KDEB_PKGVERSION=7.1.0-1 \
  KDEB_CHANGELOG_DIST=unstable \
  bindeb-pkg
```

The build is unprivileged. Do not use `sudo` for compilation or packaging.
The packaging target invokes `dpkg-buildpackage` and writes packages in the
parent directory, `/usr/local/src` for this checkout.

The expected packages are approximately:

```text
linux-image-7.1.0-debplus.1_7.1.0-1_amd64.deb
linux-headers-7.1.0-debplus.1_7.1.0-1_amd64.deb
linux-image-7.1.0-debplus.1-dbg_7.1.0-1_amd64.deb
linux-libc-dev_7.1.0-1_amd64.deb
```

The exact set is generated by
[`scripts/package/mkdebian`](/usr/local/src/linux/scripts/package/mkdebian#L203-L263).

### 5. Inspect and install deliberately

Inspect package metadata and contents before installation:

```sh
dpkg-deb -I /usr/local/src/linux-image-7.1.0-debplus.1_7.1.0-1_amd64.deb
dpkg-deb -c /usr/local/src/linux-image-7.1.0-debplus.1_7.1.0-1_amd64.deb
dpkg-deb -f /usr/local/src/linux-image-7.1.0-debplus.1_7.1.0-1_amd64.deb Installed-Size
```

Check every destination filesystem immediately before installation:

```sh
df -h / /usr/local/src /boot /efi
```

This host's systemd-boot hook calls `kernel-install`, which copies the kernel
and generated initramfs into `/efi`. The current 173 MiB of ESP headroom is much
tighter than root-disk space, and an ESP copy failure can leave the package
unconfigured. Remove an intentionally obsolete kernel or increase ESP capacity
before installation if the new kernel and initramfs will not fit. The debug
package consumes root filesystem space, not ESP space; inspect its
`Installed-Size` separately.

Install the image and headers using exact filenames:

```sh
sudo apt install \
  /usr/local/src/linux-image-7.1.0-debplus.1_7.1.0-1_amd64.deb \
  /usr/local/src/linux-headers-7.1.0-debplus.1_7.1.0-1_amd64.deb
```

Do not install the generated `linux-libc-dev` package unless intentionally
replacing Debian's userspace kernel headers. It is not required to boot this
kernel or build ordinary external kernel modules.

The image package invokes the standard `/etc/kernel` and `/usr/share/kernel`
maintainer hooks. On this host those hooks generate the initramfs and the
systemd-boot entry. Packaging does not require hand-copying `bzImage` into the
EFI System Partition.

### 6. Preserve or install debug symbols

The current config enables `CONFIG_DEBUG_INFO`, so packaging emits a separate
`-dbg` package. Keep that package with the exact image package even if it is not
installed immediately.

Installing it provides the unstripped `vmlinux`, module debug files, build-ID
links, and `/usr/lib/debug/vmlinux-<release>`, which the kernel packaging script
creates specifically for kdump tools. See
[`scripts/package/builddeb`](/usr/local/src/linux/scripts/package/builddeb#L108-L136).

```sh
sudo apt install \
  /usr/local/src/linux-image-7.1.0-debplus.1-dbg_7.1.0-1_amd64.deb
```

For this repository's crash-diagnostic objective, retaining the debug package
is recommended. A vmcore without exact matching symbols loses reliable
structure layouts, source lines, and module stacks.

### 7. Select the first boot safely

Inspect the entry created by package hooks:

```sh
bootctl list
```

Use the new entry once while retaining the established default:

```sh
sudo bootctl set-oneshot <new-entry-id>
sudo systemctl reboot
```

After boot, verify the selected release and its diagnostics before changing the
default:

```sh
uname -r
cat /proc/cmdline
journalctl -b -k --no-pager
```

Apply and verify the Compfuzor pstore policy before destructive crash tests.
Kdump installation, storage policy, arming, and testing remain separate steps.

## Debian packaging targets

Linux 7.1 exposes three Debian targets through
[`scripts/Makefile.package`](/usr/local/src/linux/scripts/Makefile.package#L83-L133):

| Target | Result | Use here |
|---|---|---|
| `bindeb-pkg` | Binary packages only | Recommended iterative workstation build |
| `srcdeb-pkg` | Debian source package only | Archive or reproduce source without compiling binaries |
| `deb-pkg` | Source and binary packages | Release-quality provenance when the source tree is prepared |

`deb-pkg` uses `git archive HEAD` for the source tarball, writes `.config` as a
Debian quilt patch, and captures `git diff HEAD` as another patch. Untracked
source files are not included. The packaging script warns about them when a
tracked diff is also present, as it is in the current Linux checkout; a tree
containing only untracked additions can pass without that warning. Always
inspect `git status` rather than relying on package output to detect omissions.

## `make deb-pkg`, `bindeb-pkg`, and `make-kpkg`

The likely remembered commands are two different systems:

- `make deb-pkg` is an upstream Linux Makefile target. It creates both source
  and binary packages using the kernel's current `scripts/package` code and
  `dpkg-buildpackage`.
- `make bindeb-pkg` is the faster upstream sibling that creates only binary
  packages.
- `make-kpkg` is the older external command from Debian's `kernel-package`
  project. It wrapped kernel builds with its own revision, initramfs, target,
  hook, and fakeroot conventions.

This machine's Compfuzor history contains an old `make-kpkg.pb` playbook, so
`make-kpkg` may be the remembered workflow. The `kernel-package` package and
`make-kpkg` command are not available in the current Debian package set on this
host. The in-tree `bindeb-pkg`/`deb-pkg` implementation is the preferred path
because it evolves with the kernel being built and uses current Debian tooling.

`make-debpkg` is not a current command or file on this host. If that name refers
to a separate personal script, it has not been found; it may instead be a memory
of `make deb-pkg` or `make-kpkg`.

## Debug symbols, stripping, and kdump

The binary image package installs module copies using `INSTALL_MOD_STRIP=1`.
The debug package independently extracts debug information from the original
unstripped build-tree modules and stores the unstripped `vmlinux`. This
separation keeps the boot package moderate while preserving full forensics.

For this kernel, a `-dbg` package does imply DWARF. The package is generated
only when `CONFIG_DEBUG_INFO=y`, and the selected
`CONFIG_DEBUG_INFO_DWARF_TOOLCHAIN_DEFAULT=y` instructs Clang to emit its
default DWARF format. The package contains:

- the complete unstripped `vmlinux` with DWARF;
- per-module debug files produced with `llvm-objcopy --only-keep-debug`;
- build-ID links for debugger lookup;
- the `vmlinux-<release>` links expected by systemtap and kdump tools.

It does not package the complete kernel source. Keep the matching source
revision and local patches separately.

BTF is different. Pahole deduplicates DWARF types into a compact `.BTF` section
that is linked into the running kernel and exposed as
`/sys/kernel/btf/vmlinux`; split BTF can also accompany loaded modules. The
current running kernel's vmlinux BTF blob is about 6.7 MiB, but the exact size
changes with each config and release. The kernel may allocate additional parsed
BTF metadata when the BPF verifier or another BTF consumer first needs it.

BTF adds build time, kernel/module size, several MiB of resident read-only type
data, and stricter module-BTF compatibility. It does not inject sanitizer-style
checks into ordinary kernel execution, so idle CPU and hot-path overhead are
normally negligible. Its runtime value is substantial: BPF CO-RE, typed
bpftrace and fentry/fexit tracing, kfunc verification, struct-ops, module type
information, and sched-ext depend on it.

Do not disable `CONFIG_DEBUG_INFO` merely to reduce the boot package. If storage
becomes a constraint, retain the generated debug package offline or use the
explicit no-debug build profile only for a separate non-forensic variant.

Record this set for each installed release:

- image `.deb`;
- debug `.deb`;
- headers `.deb` if external modules are used;
- exact final `.config`;
- source commit and local patch commit;
- `clang --version`, `ld.lld --version`, and Rust toolchain versions; and
- package build log.

## Reproducibility controls and limits

For repeatable metadata, pin values that otherwise depend on the current clock,
user, and hostname:

```sh
export SOURCE_DATE_EPOCH="$(git -C /usr/local/src/linux show -s --format=%ct HEAD)"
export KBUILD_BUILD_TIMESTAMP="$(git -C /usr/local/src/linux show -s --format=%cI HEAD)"
export KBUILD_BUILD_USER=rektide
export KBUILD_BUILD_HOST=darkstar
export KDEB_CHANGELOG_DIST=unstable
```

The kernel's [reproducible-build documentation](https://docs.kernel.org/kbuild/reproducible-builds.html)
also warns about absolute debug paths, uncommitted Git state, generated source
files, structure-randomization seeds, and module signing.

These variables improve kernel reproducibility but do not by themselves make
the `.deb` files byte-for-byte reproducible. Linux 7.1's `mkdebian` writes the
current `date -R` into `debian/changelog`, and `SOURCE_DATE_EPOCH` does not
replace that call. Fully repeatable packages require deterministic changelog
generation in addition to fixed distribution, package version, paths,
compression, tool versions, and kernel metadata.

The current configuration has `CONFIG_MODULE_SIG_ALL=y` and points
`CONFIG_MODULE_SIG_KEY` at `certs/signing_key.pem`. Kbuild generates a temporary
key when that file does not already exist, so independently repeated builds are
not byte-for-byte reproducible. Secure Boot is currently disabled, making that
acceptable for the baseline. A reproducible or Secure-Boot-enabled flow needs a
separately managed persistent key policy; never commit a private signing key to
this repository.

Committing the four AMDGPU source changes in a local Linux source revision is
preferable to merely suppressing `-dirty` with `LOCALVERSION`. A commit records
the exact patch and lets source-package generation reproduce it.

## Ccache

The kernel documents this Clang form:

```sh
SOURCE_DATE_EPOCH="$(git -C /usr/local/src/linux show -s --format=%ct HEAD)" \
KBUILD_BUILD_TIMESTAMP="$(git -C /usr/local/src/linux show -s --format=%cI HEAD)" \
make -C /usr/local/src/linux -j16 \
  LLVM=1 CC="ccache clang" \
  LOCALVERSION=-debplus.1 \
  KDEB_SOURCENAME=linux-debplus \
  KDEB_PKGVERSION=7.1.0-1 \
  KDEB_CHANGELOG_DIST=unstable \
  bindeb-pkg
```

Ccache is useful for repeated edits that recompile many of the same translation
units, but it is not automatically better for every kernel build.

Potential downsides:

- The first build can be slightly slower because ccache hashes inputs and writes
  the cache while receiving no hits.
- The cache consumes additional disk space and needs an explicit size and
  eviction policy. That matters on this 97%-used root filesystem.
- Kernel configuration, generated headers, compiler versions, flags, source
  paths, and timestamps can invalidate broad portions of the cache. A changing
  `KBUILD_BUILD_TIMESTAMP` can destroy the expected hit rate.
- Ccache accelerates compilation, not the expensive final LTO link. Its relative
  value is lower for ThinLTO and Full LTO builds.
- A cache hit can complicate diagnosis of a compiler regression or suspected
  stale/corrupt build. Reproduce build-system bugs once with ccache disabled and
  a clean output directory.
- Shared or remote caches are a supply-chain trust boundary: cached objects
  become executable kernel code. Do not consume a cache writable by untrusted
  users.
- Cache statistics can create false confidence. A high hit rate says inputs
  matched cache keys; it does not prove reproducibility or correctness.

Use ccache only after one ordinary Clang build succeeds. Pin deterministic
metadata, record `ccache --version` and `ccache -s`, set a bounded cache size,
retain the package-compression exports from the baseline build, and disable
ccache when investigating toolchain behavior.

## Storage and build-tree strategy

The current source checkout already occupies about 26 GiB and the root
filesystem has about 127 GiB free. An in-place compiler switch will rebuild most
objects but reuse the existing object paths. A fresh out-of-tree build can
consume another source-tree-sized allocation before packages and debug symbols
are written.

Monitor free space throughout the first Clang build. Package creation writes to
`/usr/local/src`, on the same filesystem. A failed package build can leave a
large `debian/` staging tree in the kernel output directory.

Also monitor `/efi` before installation. Root may have room for compilation
while the much smaller ESP lacks room for another kernel and initramfs. On this
host the package post-install hook invokes `kernel-install`, and failure to copy
either artifact aborts the hook.

For long-term cleanliness, prefer a clean Git/Jujutsu worktree or exported
source plus an output directory on a filesystem with deliberate capacity. The
current source tree contains old in-tree output, so Linux refuses to use it as
the source for a separate `O=` output. Do not run `make mrproper` casually: it
deletes the current config and generated state.

## Package compression

Kernel packaging accepts `KDEB_COMPRESS`, but Linux 7.1 marks it for future
removal in favor of dpkg's `DPKG_DEB_COMPRESSOR_TYPE`. Compression changes
package creation time, package size, and installation decompression cost; it
does not change the kernel image itself.

The archival recommendation for this host is:

```sh
export DPKG_DEB_COMPRESSOR_TYPE=xz
export DPKG_DEB_COMPRESSOR_LEVEL=9
export DPKG_DEB_THREADS_MAX=16
```

Installed dpkg 1.23.7 supports `xz` levels 0 through 9 and defaults to level 6.
Level 9 spends more CPU time and memory during package creation in exchange for
smaller retained `.deb` files. `DPKG_DEB_THREADS_MAX=16` allows the compressor
to use this host's CPUs while remaining an upper bound rather than a promise
that every archive member will parallelize fully.

Keep the legacy `KDEB_COMPRESS` variable unset because the `-Z` option it
generates overrides `DPKG_DEB_COMPRESSOR_TYPE`. The thread limit applies to each
compressor process, not to the package build globally; concurrent package
compression can therefore exceed 16 total threads and make xz level 9 consume
substantial memory. Lower `DPKG_DEB_THREADS_MAX` without changing level 9 if
packaging causes memory pressure.

This setting compresses the package's control and data archives. It does not
reduce installed disk use, ESP use, the in-memory kernel, or the generated
initramfs. Kernel images and xz-compressed modules may gain little from another
compression layer; the debug package's DWARF data is more likely to benefit.
Measure the first package set before assuming a large saving.

Xz level 9 is the size-oriented baseline. Zstd is a valid faster alternative,
including high levels up to 22, but generally trades some archive density for
much faster compression and decompression. Do not add xz's `extreme` strategy
to the baseline: dpkg exposes it as an additional command option, not through
the two compressor environment variables, and its extra build cost needs a
measured justification.

These variables apply to newly built binary packages. Repacking an existing
`.deb` changes the archive bytes and invalidates any detached checksum,
`.changes`, repository signature, or prior build attestation associated with
that file. Keep original release artifacts intact unless intentionally issuing
a newly identified package build.

For `deb-pkg` or `srcdeb-pkg`, source-tar compression is separate. Set
`KDEB_SOURCE_COMPRESS=xz` if the source archive should also favor size.

## Alternate flows

Treat every alternate as a separate build product. Use a separate output tree,
unique `LOCALVERSION`, unique `KDEB_SOURCENAME`, and unique
`KDEB_PKGVERSION`. This prevents compiler or LTO objects from contaminating one
another and prevents fixed-name `linux-libc-dev`, `.changes`, and `.buildinfo`
outputs from representing different variants under one package identity.

### GCC/binutils fallback

Regenerate from Debian's base config using `overrides.config` and
`overrides.gcc`, then omit `LLVM=1` from every command. Give the result a
different release name so it can coexist with the Clang build:

```text
LOCALVERSION=-debplus-gcc.1
KDEB_SOURCENAME=linux-debplus-gcc
KDEB_PKGVERSION=7.1.0-1gcc1
```

Upstream x86 Kconfig does not expose a GCC LTO mode. The fallback therefore uses
GCC's conventional `-O2` build and GNU binutils. It is valuable for diagnosing
a Clang-specific build or runtime regression, not as a second canonical build.

### ThinLTO experiment

Create a separate LLVM experiment fragment rather than modifying
`overrides.llvm`:

```text
# CONFIG_LTO_NONE is not set
CONFIG_LTO_CLANG_THIN=y
# CONFIG_LTO_CLANG_FULL is not set
```

This experiment is not compatible with the canonical Linux 7.1 feature set.
With BTF enabled, Kconfig disables Rust and consequently removes the DRM panic
QR screen and Rust drivers. Disabling BTF preserves Rust and ThinLTO but removes
BPF CO-RE kernel type data, typed bpftrace/fentry facilities, module BTF, and
other BTF-dependent BPF interfaces. Do not promote ThinLTO while both Rust and
BTF remain requirements.

Use a distinct `LOCALVERSION`, retain the same common config, and compare build
time, peak memory, image size, boot behavior, representative workload results,
and external module builds. Do not promote ThinLTO based only on a successful
compile.

For example, use `LOCALVERSION=-debplus-thinlto.1`,
`KDEB_SOURCENAME=linux-debplus-thinlto`, and
`KDEB_PKGVERSION=7.1.0-1thinlto1` in an isolated output tree.

### AutoFDO and Propeller

Use these only as a dedicated profiling project. AutoFDO requires a training
kernel, representative `perf` branch samples, profile conversion, and an
optimized rebuild with `CLANG_AUTOFDO_PROFILE=<file>`. Propeller can be trained
standalone, but its recommended use over AutoFDO, AutoFDO plus ThinLTO, or
instrumented FDO adds a second training and rebuild cycle using both compile and
link profiles. Keep profiles versioned with the source, config, workload
definition, and hardware context.

### Lean binary build without debug package

The source package name controls Debian build-profile names. Give the lean
variant its own source and package versions, then omit the debug package using:

```sh
source_tree=/path/to/clean-linux
output_tree=/path/to/linux-debplus-lean-out

DEB_BUILD_PROFILES=pkg.linux-debplus-lean.nokerneldbg \
make -C "$source_tree" O="$output_tree" -j16 \
  LLVM=1 LOCALVERSION=-debplus-lean.1 \
  KDEB_SOURCENAME=linux-debplus-lean \
  KDEB_PKGVERSION=7.1.0-1lean1 \
  KDEB_CHANGELOG_DIST=unstable \
  bindeb-pkg
```

This saves packaging space but is not recommended for the crash-forensics
kernel. `pkg.linux-debplus-lean.nokernelheaders` similarly omits the headers
package, which prevents ordinary DKMS/external-module development for that
release.

### Full Debian source and binary release

Use `deb-pkg` instead of `bindeb-pkg` when source provenance is part of the
deliverable. First commit required source changes and remove or account for
untracked files. The target creates an original source archive, Debian source
metadata, config and local-diff patches, binary packages, `.changes`, and
`.buildinfo`.

The generated Debian source does not encode `LLVM=1` in `debian/rules` and does
not declare Clang, LLVM, Rust, bindgen, or pahole as build dependencies. A later
ordinary `dpkg-buildpackage` therefore defaults to GCC and can change
compiler-gated Kconfig choices. Provision the complete toolchain and pass the
same policy explicitly when rebuilding:

```sh
export SOURCE_DATE_EPOCH="<recorded Unix epoch>"
export KBUILD_BUILD_TIMESTAMP="<recorded date>"
export KBUILD_BUILD_USER=rektide
export KBUILD_BUILD_HOST=darkstar

LLVM=1 DEB_BUILD_OPTIONS=parallel=16 \
  dpkg-buildpackage --build=binary
```

For a durable LLVM source package, consider patching its `debian/rules` and
`Build-Depends` so the toolchain policy is encoded rather than supplied by
operator memory.

### Source package only

Use `srcdeb-pkg` when archiving or transferring the exact source package without
spending resources on a binary build. A controlled builder must still provision
and pass the LLVM and reproducibility policy described above; ordinary Debian
defaults do not preserve it.

### Clean out-of-tree build

Create a clean worktree or source export, apply the AMDGPU hotfix there, put the
normalized config in a separate output directory, and invoke every command with
the same `O=<output>` and `LLVM=1` values. This is cleaner and easier to discard,
but requires enough space for a second complete build tree.

### Signed kernel or Unified Kernel Image

Secure Boot is currently disabled, so signing is not a baseline requirement. A
future systemd-boot flow can use a Unified Kernel Image containing the kernel,
initramfs, command line, and metadata, signed by an enrolled key. Treat kernel
image signing, module signing, key enrollment, TPM measurement, and recovery-key
storage as one designed chain rather than adding `sbsign` as an isolated final
command.

### Historical `make-kpkg`

Recreating the old `make-kpkg` workflow would require restoring the external
`kernel-package` tooling or maintaining a private replacement. It adds another
policy layer without improving compatibility with current Linux packaging
scripts. Keep the old Compfuzor playbook as historical evidence, but use
`bindeb-pkg`, `srcdeb-pkg`, or `deb-pkg` for new builds.
