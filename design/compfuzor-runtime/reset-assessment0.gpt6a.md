# Recommendation

**Build CFR as a shared Effect-native composition environment over domain-owned
operations. Replace the competing composition authorities, not the domains that
already know how to commit their work.** Its characteristic capability should be
that the same independently authored operation is discoverable, composable,
target-bound, inspectable, and callable through a library or a narrow/broad CLI.

The [new draft](reset-draft0.gpt6a.md) is the proposed destination. This assessment
explains why it differs from [draft2](effect-draft2.gpt6a.md). Neither document is
acceptance or implementation authorization. FX's recovery is a valuable map; the
important architectural conclusions below were checked against the named original
documents and current source, not inherited as authority from its status labels.

## 1. Preserve the ambition; change the unit of replacement

The [composition brief](composition-problem0.gpt6a.md#concrete-design-tests) asks
for considerably more than a cleaner shell runner: open contribution, meaningful
narrowing, reusable programs, material/exposure relationships, confext construction,
and bootstrap before a project's first write. The [experiment disposition](experiments0.gpt6a.md#experiment-4--parent-assessment-and-end-of-sequence)
correctly says the four probes did not deliver an integrated backbone.

Those goals remain useful. What changed is the evidence about **where integration
should stop**:

| Earlier question | What current work establishes | Architectural consequence |
|---|---|---|
| Can one implementation serve varied configuration? | Complete definitions already independently compile/bind recipes, contexts and owners. | CONFIG instance identity is `(deployment, definition)`, never a partition of a global bag. |
| Can generic composition select domain work before effects? | Audience actions prepare CONFIG/keybinding operations and preserve selected receivers through body environment changes. | Reuse admission as a domain boundary; replace the closed compositor dispatch, not its guarantees. |
| Does contribution require a new fuze manifest? | Proxy material enters ordinary ENV recipes and normal ZIM import with explicit order. | Native material plus an explicit parent input/membership link is often enough. |
| Can receivers advertise themselves? | Rendezvous supports owner-held declarations, overlays, masks, and frozen domain batches. | Use this for receiver discovery; it is neither the executable catalog nor accepted membership. |
| Is environment just one loaded map? | Exact projections and the shell probe distinguish defaults, observed values, management, and derived candidates. | Shared init exposes selected domain views, not one universally merged Environment. |
| Does the shared binary eliminate deployment packaging problems? | Current JS and workers still infer deployment from executable paths. | Root/resource decoupling is required; a global symlink alone is not migration. |

Keep the fixed CONFIG commands, user/context defaults, copy/link/assembly choices,
status explanations, LINKS lifecycle, Zim channels/caches/loaders, independent Mise
blocks, and no automatic pruning. The [simplification plan](../../doc/config/simplification.md#position)
is stronger as a product-contract/deletion test than as a current implementation
roadmap. Its old built-JS-only rule conflicts with the later explicit native-TS
direction and its own subsequent ENV Python exception. Resolve that tension openly:
one supported package/dependency delivery mechanism, with native TS authoring, is
the new recommendation; language purity is not a useful invariant.

## 2. Current-code findings that materially constrain the reset

### Complete CONFIGs already provide the needed isolation

[`compile_definitions`](../../library/filter_plugins/config_definitions.py) invokes
ordinary recipe/context compilation per definition, checks output and command
collisions, emits each spec, and deduplicates the stock worker. Its
`instances.json` is a generated local index. Replacing it with another authored
manifest would add indirection without adding meaning.

[`admitConfigCommand`](../../files/config/runtime.ts) freezes context paths and
strategy for audience-bound operations. The low-level unbound path does less
freezing, so its return type must not be overread as universal immutable admission.
Several helpers still read `process.env`. A new in-process adapter needs explicit
environment parameters before claiming per-run isolation. Until then, use the
existing prepared/opaque boundary; do not temporarily swap global `process.env`.

[`runAssemblyResult`](../../files/config/assembly.ts) is a **complete operation**:
it binds a spec and runs the existing worker, which validates and commits candidates.
It is not a prepare stage that CFR should follow with its own publisher. CONFIG's
transaction includes domain supplemental candidates and validation hooks; a shared
runtime does not get to split it just to display a prettier pipeline.

The worker closure is larger than `config-run.sh`: recipe leaves/processors,
validation hooks, helper assets, and possibly fuzings callbacks also participate.
The adapter currently derives cwd/DIR from the runner path, while the worker can
restore `deploymentRoot` from the spec. These partially overlapping corrections
are concrete reasons to introduce **explicit deployment and resource bindings**,
not to move the runner file and hope path inference continues to work.

### Fanout is already a deliberate partial-success operation

[`config-remote`](../../files/config-remote/runtime.ts) reads selected definition
specs, resolves/admit-checks every match, then performs link plus rebuild with
per-target rollback. Later admitted targets are attempted even if an earlier one
fails. The [tests](../../tests/integration/config_definitions.test.py) specifically
replace a later spec during an earlier validator and assert frozen binding survives.
This is useful native domain semantics, not a generic collector's default fail-fast
loop. CFR should expose one batch result with per-target outcomes, retaining the
domain's continuation policy and successful earlier commits.

### Audience actions solved real admission, but are a second composition engine

[`operations.ts`](../../files/actions/operations.ts) already reuses domain-local
admit/apply functions. [`runtime.ts`](../../files/actions/runtime.ts) preflights the
graph, prepares typed operations before authored bodies, retains shell setup and
routes children. Its private JSON transport is a live process bridge, not history.
The [tests](../../tests/integration/action_domains.test.py) exercise preparation
before bodies and prevent later strategy/HOME/profile changes from redirecting work.

Retain those behaviors. Retire the `PreparedOperation` central domain union and
independent action execution loop **when their selected aggregates become CFR-owned**.
The transport remains necessary while a shell body owns later child execution;
it can disappear from a native aggregate without declaring all shell bridges obsolete.

### Rendezvous is useful precisely because it is not universal

[`inspectRegistry`](../../runtime/registry/read.ts) delegates observation/loading
to Figments, decodes whole declarations, retains disabled/invalid states and refuses
lookup on incomplete observations. Domain selection then adds captured-byte/topology
guards. This is a good reusable discovery substrate, not proof that one universal
registry should own modules, configurations, receivers, and execution history.

Preserve the [current registry contract](../../runtime/registry/README.md): masks
do not fall through; force-enable does not unmask; advertisement is not accepted
membership. Current Zim advertisements do not yet replace its explicit host import
bridge. Do not silently commission that separate adoption through the reset.

### Proxy adoption is the counterexample to mandatory descriptors

The [real playbook](../../opencode-bus-proxy.src.pb) selects service+priority files
and a distinct client file, assembles ENV before Rust and normal Zim import, and
keeps systemd service publication separate. The [report](../fuzings/proxy0.gpt61sol.md)
records isolated execution, not live deployment. A plain native module and parent
input link suffice; the broader experimental enrolled-root resolver contributes no
essential capability to this concrete path.

[`config-env.py`](../../files/config-env.py) is the actual literal parser. Extend
that reducer for source-aware reads rather than grow another TypeScript dotenv
grammar. The [environment probe](environment1.gpt61sol.md) reports nine scenario
groups and focused native-args checks. Its results establish a useful local
decision contract, not Effect integration, generalized shell ownership, or resume.

## 3. Substantial options and selection

| Option | Strength | Cost or failure | Decision |
|---|---|---|---|
| Extend audience actions into CFR | Immediate compatibility and tested admission | Keeps closed domain dispatch, shell transport and compiled action graphs as the authoring center | Adapter, not destination |
| Author a CFR program algebra as draft0 | Exact inspection of explicitly represented structure | Duplicates sequencing and invites a second workflow language; dynamic bodies still opaque | Do not require it |
| Annotated native Workflow/Activity, plus explicit collection snapshots | Native composition, ordinary services, broad contribution; exact known selections | Requires honest dynamic boundaries and occurrence discipline | **Select**, refining draft2 |
| Universal material/route/publication registry | One apparently uniform plan | Reassigns domain ownership and makes ordinary work pay for unused metadata | Reject |
| Native domain data with optional material projections | Preserves existing schemas; makes packaging/placement inspectable when needed | Some operations remain opaque until their owner supplies a projection | **Select** |
| Persist full durable execution immediately | Strong eventual resumption story | Code closure, state transitions and host effects are not yet replay-safe | Separate later capability |
| Durable invocation history with finite fresh execution | Useful accountability now, without fictional exactly-once claims | An interrupted operation may remain unknown | **Select first** |

This is not a return to the final experiment's unstructured dispatcher. Public
memberships and collection snapshots are first-class; a resolved static collection
is the same data the runner consumes. Native workflows expose optional **outlines**
for their internal order. An outline is explicitly weaker than an executable plan.
The CLI must keep catalog, exact collection/admission plans, and actual trace apart.

The earlier composition drafts help make the choice precise. The GLM proposal's
different broad/narrow lane semantics make narrowing surprising; reject that.
The Sol proposal's route-join identities and explicit publication edges are useful,
but a required project manifest and full asset ledger are unnecessary prerequisites.
Neither a compiled Ansible-only catalog nor a mandatory publication ledger is the
new authority. Selection snapshots belong to invocations; declarations stay native.

## 4. Effect API findings and consequences

The project pins **effect/platform-node 4.0.0-rc.118**. Installed source and its
`AGENTS.md` take precedence over older skill examples (`Effect.Service`, older CLI
packages, etc.). No internal Effect opcode inspection is justified.

| Source observation | Consequence |
|---|---|
| Activity has name, schemas, annotations, and execute; no separate input schema or public rename operation. | Public activity binding needs an explicit typed input contract. Do not clone its retry-wrapped execute into another Activity casually. |
| Memory lookup is `executionId/activity.name/attempt`. | Calling one Activity twice with changed Context is not two occurrences. |
| Workflow execution ID hashes tag plus `idempotencyKey(payload)`. | Include a fresh root run ID and explicit occurrence path; deployment identity is not an idempotency key. |
| Engine registration is keyed by Workflow tag and captures service context. | Register once per run scope; bind varying invocation data through payload/request services, not repeated registration of one tag with different closures. |
| Activity defaults retry interruptions, and exhausted interrupt handling can become a defect. | Legacy mutation admission must explicitly disable retries and preserve the external signal outcome at the invocation boundary. This needs a focused conformance test, not an assumption. |
| A suspended Activity may rerun its body; only completed results are cached. | No invisible RunData mutations inside cacheable activities; no claim that native Effect automatically makes host effects replay-safe. |
| `layerMemory` is in-memory; EventLog commits after its handler succeeds. | Durable history needs explicit integration. Never run provisioning inside a lifecycle-event handler. |
| File handles expose `writeAll`/`sync`; process examples expose scoped spawners and `extendEnv`. | Use existing Effect capabilities for a small history writer and explicit process projection instead of a new engine. |

**Recommended occurrence solution:** admit an Activity through a native child
Workflow boundary whose execution key includes its occurrence. That workflow
yields the original Activity once with its admitted inputs. Distinct child
executions isolate Activity result keys without renaming or wrapping its already
retry-wrapped body. This is a source-supported design, not tested integration.
For new composite work, ordinary public Workflows already supply the boundary.

The cost is one small boundary execution per public Activity; it is preferable to
inventing a renaming protocol. Private Activity reuse inside a domain Workflow
remains the domain author's responsibility. A static validator cannot discover all
future generator calls. Direct native calls remain possible; managed CFR guarantees
apply to admitted calls and contributed workflows, not arbitrary trusted code.

## 5. The most important refinement: three kinds of state

Draft2's mutable collaboration is right. A single mutable bag is insufficient as
an explanation of authority:

1. **Original facts and bindings:** request, selected provider, deployment identity,
   observed defaults/specs, and admitted destinations. Keep these immutable.
2. **Run workspace:** typed mutable inputs/settings/candidates/results, partitioned
   by domain and complete target identity; explicit revisions and writers.
3. **Domain-owned persistence:** CONFIG outputs/membership, receiver registration,
   and a particular live shell's managed-value receipt. CFR history records these
   operations; it does not replace their authority.

Mutable settings can affect a **later** admission. They cannot redirect an already
admitted receiver. A domain operation can add output data to the workspace, but
its transaction owns whether those outputs committed. A shell's receipt advances
only after that shell applies and acknowledges; launching a child does not do so.

For later replay, a cached Activity result must include the data used by the
surrounding workflow's explicit state transition. Reconstruct the workspace from
its beginning or a position-matched checkpoint, never final state followed by early
updates. Stable transition identity, ordering, before revision and validated after
value must agree. Failed/partially mutating operations cannot fabricate a successful
transition envelope. **Do not implement draft2's generic hidden-write capture helper
in the first landing.** It widens both transaction and replay promises unnecessarily.

## 6. Sourcing, discovery and bootstrap need one bound invocation

The [sourcing direction](../runtime-sourcing/direction0-syn.gpt61sol.md#2-keep-three-catalogs-and-two-roots-distinct)
distinguishes implementation, workload and receiver catalogs. Preserve it. Policy
selects one provider closure using `changed → canonical → deployed`; the deployment
still supplies its own work and data. Default module-directory discovery collects
contributions, while receiver rendezvous selects domain targets. These are three
operations with different cardinalities, not three names for one registry lookup.

The shared host entry needs a small dependency-independent locator path. A checkout
can run its own installer locally once Node and the provider closure exist. That
operation exposes the host entry; it must not resolve itself through the missing
entry it is installing. A missing/incompatible provider yields an actionable error,
not regeneration of shell compositors or fallback after a partially failed mutation.

The unresolved delivery problem is concrete: arbitrary deployment-local TS does
not resolve a globally installed `effect` automatically. The new draft recommends
a host ABI package slot plus ordinary package links for native modules, pinned for
a whole invocation, rather than a custom TypeScript loader. This is a stronger
host prerequisite and needs an outside-checkout implementation demonstration.

## 7. Material and adoption tests must remain in the destination

Confext is not displaced by ENV. It is the best second-domain test that CFR can
compose **data interpreted by another consumer**, rather than only run commands.
Keep byte ownership, exposure edges and artifact destinations separate. The
[corrected research](../confext/build-inputs1.fx.md#2-what-the-iface-playbooks-actually-generate--the-byte-trace)
shows useful existing iface bytes and LINKS mappings, but modes need explicit
resolution. Packaging should reuse existing bytes, report assumed versus observed
facts, and require no CFR receipt or project-contained layout beforehand.

Likewise the reported dangling `/opt/zim-main` aliases are a dated failure-class
observation from FX, not a live-health finding made here. Shared code still needs
representation cutover: verify the replacement target/worker closure before
switching public entries, refuse unexamined file→symlink collisions, and remove only
explicitly approved obsolete paths. No-prune is not permission to leave a newly
declared command knowingly dangling; no-force is not a migration plan by itself.

## 8. What should actually disappear

- New CFR-owned aggregates stop emitting both shell `run_all` and native flow plans.
  Retire `files/flow`/indexed-flow execution for migrated deployments; keep old
  deployments served until their explicit cutover.
- The new catalog projects admitted native definitions and compatibility records;
  it stops reclassifying filenames as another independent scheduling authority.
- Native aggregates no longer need action-session transport or the closed central
  domain switch. Opaque shell-owned aggregates retain the existing bridge intact.
- Shared-provider adoption stops copying the omnibus and shared worker closure into
  every migrated deployment. Workload-specific leaves remain deployment material.
- Native selected-env consumers stop whole-`env.export` loading. The proxy refresh
  adoption eventually replaces its competing source-time default writer; merely
  adding a second writer is not completion.
- Do not promote the experimental general fuzings resolver or old program/service
  locator prototypes into prerequisites. Delete their replacement-only paths after
  caller/reference review, not by sweeping historical material or deployed files.

## 9. First useful checkpoint and consequential human choices

Start with the [environment report's bounded selected-view/pure-resolver/proxy
bridge](environment1.gpt61sol.md#6-smallest-useful-new-cfr-slice), authored in the
new runtime's domain home. It immediately makes defaults findable while preserving
local changes. Keep it importable and explicitly invoked; it does not need the
entire execution environment to be useful. Its next integration checkpoint must
use the proposed common entry, not merely rename the existing multicall command.

Then commission an **integrated replacement**, not another toy backbone: host/local
entry over a different deployment; one real opaque authored bin; one pure aggregate
with its old composition retired; one native environment operation; explicit init
adjustment consumed twice; repeated status before/after work; recorded history and
failure/interruption. Preserve complete CONFIG admission/transactions through an
adapter in that same seam before broadening migration.

Consequential choices remain for review, with recommendations in the draft:

- Accept the host ABI/package layout and Node prerequisite, rather than rely on
  undocumented global module resolution.
- Accept native workflows plus exact collection snapshots/declared outlines,
  rather than demand a statically exact plan of every TypeScript branch.
- Accept fresh finite execution plus durable history first; durable resume is later.
- Confirm proxy bootstrap empty semantics, managed-empty/absent behavior, and the
  explicit pin/reset vocabulary before startup adoption.
- Choose confext release compatibility policy and output format at its landing;
  directory form with explicit host compatibility is the recommended first build.
