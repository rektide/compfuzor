# A host runtime over project-local route and publication ledgers

## The question and the bet

Compfuzor already composes shell bins, records parts of their provenance in a
catalog, and renders LINK destinations. These three views disagree about what
constitutes a command or a build input. The operator wants narrower/broader
commands, easy TypeScript contributions and script interrogation, and a
project-contained tree that can still be installed at host paths. Building an
iface confext **without installing or activating it** is the immediate test.
An early common runtime is acceptable; this very young runtime can change
substantially. Research question: *if the runtime is installed on the host once,
what is the smallest project-local declaration that makes commands, generated
materials, and their delivery independently inspectable?*

**Proposal:** install `cfr` once per host. Each project carries a registry of
actions and **route joins**, plus a ledger of files and **publication intents**.
An action is a callable capability; a route is an operator-facing selection of
calls; a publication intent says where already-rendered bytes may appear. None
of these three is inferred from another's spelling. A phase is an ordered
barrier *within one route invocation*, not a wrapper or a property of a
subsystem. The runtime assembles an immutable, explainable plan before running
it. This is not a general task graph or a new rendering engine.

The [problem brief](/design/compfuzor-runtime/composition-problem0.gpt6a.md)
is the operator brief, not an accepted implementation spec; the interfaces
below are proposed. I did not read any other current-wave composition draft.

## Boundaries: host, project, action, route

```text
host (once):  /usr/local/bin/cfr -> versioned host installation
              Node >=24; built-in LINKS delivery, legacy exec, confext build,
              project-root preparation; versioned registry contract

project:      <PROJECT>/registry/project.json       # roots, version, module list
              <PROJECT>/registry/modules/*.ts      # trusted project additions
              <PROJECT>/registry/render.json        # Ansible-derived asset ledger
              <PROJECT>/material/{etc,src,opt,...}  # authored/generated bytes
              <PROJECT>/commands/...                 # legacy executable leaves
              <PROJECT>/outputs/confext/...          # built artifact, not installed

plan:         cfr --project <PROJECT> plan apply/network --json
run:          cfr --project <PROJECT> run apply/network
```

These are domain-grouped directories, *illustrative* new-project layout, not
an instruction to move existing `/etc/opt/<NAME>` deployments today. `NAME`
identifies a project; `--project` selects its instance/root, never a global
search for the first `NAME` match. System versus user is an explicit target
qualifier (`--scope system|user`); another host/project requires another
invocation, unless a conspicuous future multi-project command is added. A
system plan must not silently absorb user actions. The host binary knows its
own installation location, not the project location from its `realpath`.

`project.json` lists module paths explicitly and says e.g.
`"requires": {"registry": "2", "runtime": ">=2.1 <3"}`. Host-builtins are
registered before those modules; duplicate action/route-join IDs or unsupported
contracts fail *before* running any plan. No implicit `bin/` scanning or
mutable host-global registry of all deployments. `cfr` cannot load modules
from a project that has not yet been materialized (see preparation below).

Authoring TS is intentionally ordinary data export. A type-only import is
erased by Node and does not require a globally installed package at runtime;
authors can install the contract package in their source workspace for checking.
Node must support the subset of TS its type stripping runs directly; dependencies
imported by contributed code are the project's responsibility. Dynamic imports
execute top-level code: these are **trusted project programs, not safe plugins**.
Module paths must be explicitly listed and confined to the project's registry
tree; registry inspection is not a sandbox. For read-only/automated listing of
untrusted projects, prefer a validated emitted JSON descriptor instead of
importing their code.

```ts
// registry/modules/network.ts (proposal, not an existing API)
import type { Contribution } from "@compfuzor/contract";

export default {
  id: "iface.extra-addr",
  tags: ["networkd", "iface", "network"], // for discovery, never automatic membership
  actions: [
    {
      id: "networkd/extra-addr.apply",
      title: "Reload networkd and reconfigure the addressed interface",
      scope: "system", effect: "mutate", risk: "network-disruption",
      handler: { kind: "exec", path: "commands/networkd/extra-addr.apply.sh",
                 protocol: "legacy-exit-v1" },
    },
    {
      id: "networkd/extra-addr.status",
      title: "Observe address, route and governing configuration",
      scope: "system", effect: "observe",
      handler: { kind: "exec", path: "commands/networkd/extra-addr.status.sh",
                 protocol: "legacy-status-v1" },
    },
  ],
  joins: [
    { id: "iface.extra-addr.change", action: "networkd/extra-addr.apply",
      bind: { interface: "enp3s0" },
      at: [{ path: "apply/network/extra-addr", phase: "change" }] },
    { id: "iface.extra-addr.observe", action: "networkd/extra-addr.status",
      bind: { interface: "enp3s0" },
      at: [
        { path: "apply/network/extra-addr", phase: "verify" },
        { path: "status/network/extra-addr", phase: "observe" },
      ] },
  ],
} satisfies Contribution;
```

The `actions` entry describes the behavior and its executable path. The join
is an explicit *bridge* from one fixed action binding to several consumer
routes. To reuse the same status action in two places, list two placements,
not two synthesized scripts or two lookalike action IDs. Another contribution
could join `networkd/extra-addr.status` under `diagnose/network` with distinct
inputs and a **different** join ID. A legacy bin can be wrapped by an action
descriptor without changing its body. `action` without any `join` is directly
callable and visible, but never in an aggregate. `tags` are descriptive; no
newly added tag can accidentally enroll a disruptive action in `apply`.

## A path is a query, not a wrapper

Route address `apply/network/extra-addr` is a declared *placement*. A query
selects placements at that path **and below it by path segment**:

```text
cfr --project P inspect routes                  # trie, counts, phases, provenance
cfr --project P inspect actions --tag networkd  # identities + direct handlers
cfr --project P inspect route apply/network     # explain members, including source joins
cfr --project P plan apply/network/extra-addr --json
cfr --project P run apply/network/extra-addr    # explicit manual invocation
cfr --project P run apply/network               # all declared network applies
cfr --project P run apply                       # all declared applies in this project/scope
cfr --project P run status/network/extra-addr   # same observe join as above
cfr --project P action networkd/extra-addr.status --json
```

`cfr inspect` and `plan` never invoke actions; the machine-readable plan
includes IDs, scope, phase, resolved binding, file provenance, policy decisions,
and handler type. A script can ask `cfr ... plan ... --json` and use `cfr ...
run ...` or `action ...` with `--input-json`; there is no convention that
requires sourcing shell helpers to discover membership. Offer `--format=ids`
for shell loops, but make structured JSON the versioned interchange. Exit and
observation protocols remain distinct; a status action need not mutate just
because its observation appears in an apply route.

Hyphens are *characters within a segment*, not recursive separators. Do not
guess `apply-network-extra-addr.sh` -> route components; that name may contain
arbitrary hyphens or systemd escape syntax. Optionally emit thin compatibility
trampolines at `bin/apply.sh` and `bin/apply-network.sh` **only** when there is
no authored file at that path; trampolines pass the project root and exact
route to the host `cfr` and print an actionable missing-runtime error. New
project-local executable names can mirror routes at `bin/routes/apply/network`
and `bin/routes/apply/network/extra-addr` (a directory and file cannot occupy
the same path, so use `.../network/_run` for every invokable trie node).
`commands/networkd/extra-addr.apply.sh` shows action identity in its path;
existing `apply-networkd.sh` may remain an action's legacy handler. The CLI
is the authoritative path interface; generated trampolines are conveniences,
not a second composition engine.

## Plan construction and order

There is one deterministic planner, not separate Python compositor and TS
flow-runner authorities:

1. Load the declared project registry, validate IDs, target bindings and
   permissions, and freeze a registry digest for this invocation. Select joins
   by segment-prefix route and exact scope; explain empty selections and reject
   unknown route prefixes rather than reporting success for typos.
2. Deduplicate repeated *join IDs with identical action+binding* inside this
   plan. If two routes place the same ID in conflicting phases, or an ID has
   different bindings, fail. **Different IDs mean different invocations**, even
   if they call the same action; this preserves intentional repeated calls.
   `apply/network/extra-addr` and `status/network/extra-addr` invoked separately
   are two plans and each may observe once. No cross-invocation caching.
3. Sort into verb-specific phase barriers, then stable explicit `order` within
   a phase and contribution/declaration order as a final tie-breaker. Proposed
   charts: `build: prepare → compile → package`; `install: acquire → publish →
   activate`; `apply: change → verify`; `status: observe`. The phase must be
   defined for the verb; aliases such as `main` exist only for legacy migration.
   Parallelism is *not* implied. Refuse a dependency on a later phase instead
   of silently moving a leaf or assuming a system-wide dependency solver.
4. Display the complete plan and effective deny-only skip reasons. Running
   proceeds sequentially; on mutation failure stop, do not run verification
   pretending success. Explicit status remains independently available.

Example: another join at `apply/network/static-only`, phase `change`, plus its
`status/network/static-only` observer placed in the apply route's `verify`
phase. `plan apply/network` runs **both change joins before either verify
join**. A `network` subsystem spanning phases is a *navigation group*, not
an atomic subprocess: `apply/network` cannot enclose all static-only steps
ahead of extra-addr's change. This fixes the existing earliest-phase placement
of a mixed-phase subsystem (see [`bin_composers.py`](/library/filter_plugins/bin_composers.py#L209-L273)).
If some network operation truly must be atomic, its owning action implements
and tests that local sequence; the route sees one call. A prerequisite that
must occur between one project's change and another's verification cannot
be expressed by a group name; put it in the appropriate phase/order or expose
an explicit separate action. This limits orchestration on purpose.

| Selecting | Illustrative plan (system project `iface-extra-addr-eno1`) |
|---|---|
| `apply/network/extra-addr` | `change iface.extra-addr.change` → `verify iface.extra-addr.observe` |
| `status/network/extra-addr` | `observe iface.extra-addr.observe` only |
| `apply/network` | all network `change` joins → all network `verify` joins |
| `build/confext/iface` | `package iface.confext.bundle` only; no LINKS apply or networkctl |

### Execution policy is not composition

Declaring/compiling a join does not autorun it. Playbook render-time triggers
are separately named (`ansible-run`); `BINS_RUN_BYPASS=True` skips those
triggers, not generation of the file or later, explicit `cfr run`. Runtime
invocations respect host-runtime bypasses (`COMPFUZOR_LINK_BYPASS`, etc.) and
explicit project/action/effect skip rules. A skip returns a typed `Skipped`
with reason, not fake success for a required artifact; a required suppressed
step makes the enclosing build *incomplete*. Scope and mutation risk are
visible in `plan`; an `apply` route is **never** made an Ansible run trigger by
default, and network-disruptive actions demand explicit invocation/acknowledgment.
Do not turn `BINS_RUN_BYPASS` into a permanent host policy: an operator may
render without applying and later call `cfr run apply/network/extra-addr`.
Conversely, `LINKS_BYPASS=True` currently prevents link-plan compilation and
thus eliminates the mapping inputs a confext build would need. Status may
still run when mutation is bypassed, using its own observation policy. A
`--force` must not silently override a concern-wide deny.

## Bold layout: project bytes and host destinations are different names

The material ledger names files by **project-relative asset ID** (e.g.
`etc/iface-static-only.network`), records origin, mode, owner/symlink nature
and expected content digest after render. Publication intents refer to those
asset IDs; they do *not* move the only copy of the file outside the project.
Two outputs can consume one asset:

```text
asset  etc/iface-static-only.network
  bytes   P/material/etc/iface-static-only.network   mode: 0644
  publish system: /etc/systemd/network/10-ens3-static-only.network
          delivery: copy, policy: replace
  build   confext: etc/systemd/network/10-ens3-static-only.network
          under P/outputs/confext/iface-static-only/...
```

Publication is an **outward edge** from project material to a host destination,
not a symlink from project material to `/etc/opt` or a requirement to write the
host path while rendering. A whole family can use one explicit outward root
edge (`/etc/opt/NAME -> P/material/etc`) *when consumers can traverse that
root*; individual systemd network files use copies when the private project
root is inaccessible to networkd. An edge's `link|copy` choice is part of its
contract, not an optimizer chosen from matching paths. Preserve original
mode/ownership in the asset ledger and allow publication-specific overrides;
the resolved target mode is explicit in the build manifest. Do not package
secrets merely because a directory is under the project root.

New projects can choose a stable policy for `PROJECT` independently of the
traditional type-specific `DIR`, with a typed mapping from `ETC_FILES` to
`P/material/etc` and `SRC` checkout to `P/material/src`. Ansible's family
writer already separates `materialized_root` from `exposure_root` in
[`artifact_links.py`](/library/filter_plugins/artifact_links.py#L124-L160),
and [`containered.yml`](/vars/containered.yml) reverses the structural link;
this proposal turns that special profile into an explicit layout contract
*and* records publication edges. One project directory makes backup/transfer
of its **bytes and declarations** feasible, not automatic host portability:
absolute paths embedded in content, user-home substitutions, host privileges,
mounts, executables, external data, and publishing edges must be inspected or
rebound on the new host. Do not claim confext solves project portability.

For existing projects an adapter can lift current `ETC_FILES` source records
and [`links.json`](/library/filter_plugins/artifact_links.py#L319-L337) into
asset and publication ledgers *if* source resolves under the selected material
root. Reject `..`, symlink escapes and overlapping/conflicting destinations;
allow external sources only as conspicuously non-portable explicit inputs.
Current `links.json` contains `src/dest/strategies` but no target mode, and
the runtime catalog contains resource references rather than bytes
([`runtime_catalog.py`](/library/filter_plugins/runtime_catalog.py#L133-L147)).
Use `links.json` as compatibility mapping evidence, not a magic complete
package manifest. Both Ansible and `cfr` should ultimately consume a
versioned *publication contract*; do not silently infer confext payload from
every file in `DIR` or all LINKS.

### Confext: a build consumer, not an install route

Contribute a package specification, not an ad hoc `install` script:

```json
{
  "id": "iface.confext.bundle",
  "action": "builtin/confext.build",
  "at": [{ "path": "build/confext/iface", "phase": "package" }],
  "bind": {
    "select": { "publicationIds": ["iface.static-only.network"] },
    "output": { "format": "directory", "under": "outputs/confext/iface-static-only" },
    "release": { "name": "iface-static-only", "id": "<selected host ID>" }
  }
}
```

Build selection uses declared *system publication intents* as candidates
but is a separate allowlist: eligible `state:present`, source a checked
regular asset beneath P, intended destination beneath `/etc`, explicit
host-visible mode, no unknown variable interpolation or unsafe symlink. Map
the destination into the confext's `/etc` subtree, then add
`etc/extension-release.d/extension-release.<NAME>` with validated host
identity/version policy. Stage privately, hash assets, refuse destination
collisions, validate the final tree, then atomically publish **only within
`P/outputs`**. Record selected IDs, source hashes, destination paths and
modes in a sidecar manifest outside the image payload. The first supported
format could be directory; `--format=erofs` requires a pinned host `mkfs.erofs`
capability. DDI/verity is an explicitly later output adapter, not silently
equated to erofs. `cfr run build/confext/iface` performs **no** LINKS delivery,
`systemd-confext merge/refresh`, systemd unit operation, or network reload.

The [confext byte trace](/design/confext/build-inputs1.fx.md#2-what-the-iface-playbooks-actually-generate--the-byte-trace)
shows why this can start with *already-rendered* iface bytes: static-only
provides a standalone `.network` file and destination; extra-addr supplies a
drop-in for a governing file and can be given `NETWORK_FILE` explicitly. These
are different target semantics, not two interchangeable labels. Present iface
sources default to mode `0660` while apply can chmod published copies to
`0644`; reject that ambiguity by declaring the bundle-bound host mode (`0644`)
before packaging. A source-inspected render-only lane uses
`BINS_RUN_BYPASS=True` *without* `LINKS_BYPASS=True`; it is not a generic
side-effect-free Ansible mode (other tasks may still mutate host state).
Confext identity paths, `CONFEXT_*` keys, and image discovery in
[`build-inputs1.fx.md`](/design/confext/build-inputs1.fx.md#1-corrections-to-archaeology0fxmd-5)
were researched against a local systemd checkout; the builder must target
the supported host version rather than assuming sysext paths. No activation
or live build test was performed in this proposal.

## Bootstrap and the pre-write lifecycle test

The host-side runtime is an **early, explicit host prerequisite**, not a
per-deployment copy slipped into each BINS list. Install/check Node, the
versioned `cfr` artifact and its checksum through a deliberately separate
bootstrap task or host playbook. This bootstrap uses Ansible/packaged files,
*not* `cfr` to install itself. Every opted-in project play then checks
`cfr --version --json` and the project contract before its first side effect;
missing/incompatible runtime fails with the bootstrap command, rather than
falling back to an obsolete project-local runtime. Legacy projects keep
their old executables until explicitly migrated. Builtins are host-versioned;
project modules/ledgers specify a compatible major and fail closed after
host upgrades. Pin an actual runtime artifact version for build provenance,
not just `>=` when reproducibility matters.

**Btrfs as a placement test, not this project's implementation:** a pre-write
`builtin/project.prepare` could accept only controller-supplied root intent
(`name`, new PROJECT path, storage kind, owner) over JSON/stdin. It cannot
depend on a project module or manifest inside an uncreated root. Place the
invocation after input normalization and runtime bootstrap but **before**
`repo_*` tasks, `fs_base`, and any other task creating `DIR`/`SRC`; current
[`compfuzor.includes`](/tasks/compfuzor.includes#L139-L186) checks out repos
before filesystem materialization, and [`repo_git.tasks`](/tasks/compfuzor/repo_git.tasks#L11-L28)
may create `DIR` itself. Validate an existing root and refuse nonempty
non-subvolume conversion instead of silently migrating. A later snapshot is
another explicit action at a chosen point; neither preparation nor snapshot
belongs in `build/confext`. This exercise proves that the runtime can be called
early without pretending its *project registry* already exists.

## What survives, what is replaced, what gets harder

| Keep/adapt | Replace/delete after parity and deliberate migration |
|---|---|
| BINS leaf bodies, wrapper helpers where valuable, author provenance, LINKS v2 as compatibility data, domain-specific CONFIG/Zim/links operations | `bin_composers.py` as the authority for new actions; shell `run_all` aggregation; partial catalog's filename classification and `build/install/status`-only flow vocabulary; per-project `compfuzor-runtime.mjs` copying and multicall alias guessing |
| Ansible's render and explicit bypasses; `run:true` legacy triggers until individually migrated | Parallel/competing TS flow and Python compositor scheduling; automatic legacy-name interpretation as permanent route IDs |

`gen_bins`' worthwhile commonality is **attribution, rendering handlers,
deduplication, and command inspection**, not necessarily emitting wrappers.
Bridge existing BINS/STATUSES once: import *authored leaf* handlers with
explicit ID/route mapping; treat generated compositors as legacy entry points
or shadow comparisons, never compose them recursively inside the new plan.
Compare representative old `run_all` order and new plan before removing
generated wrappers. Hand-authored `apply.sh` is one opaque action until split;
do not mislabel it a composed root. Execution authority moves project by
project, not because a catalog happened to be emitted. The existing runtime
already recognizes `apply` actions but not apply flows
([`runtime_catalog.py`](/library/filter_plugins/runtime_catalog.py#L16-L27),
[`apply-flow0.glm53.md`](/design/compfuzor-runtime/apply-flow0.glm53.md#state-of-the-world-verified-this-session));
merely adding that fourth string would not fix the divided authority.

Two competing architectures were considered:

1. **Universal graph / material IR.** Nodes for every Ansible task, file,
   effect and installer promise arbitrary recomposition. Rejected for this
   attempt: most old scripts have opaque effects, resources such as CONFIG/Zim
   have their own meaningful order, and graph vertices would falsely certify
   build purity. Explicit routes and asset publication narrow the promises.
2. **Retain generated shell compositors; teach catalog their names.** Cheaper
   for `apply.sh`, but hyphen parsing never yields general traversable paths,
   subsystem wrappers violate global phase barriers, multiple membership
   yields cloned glue, and confext selection still needs separate data. Keep
   those wrappers during transition, not as the new design's authority.

The cost of this proposal is a strong Node/host-bootstrap assumption, trusted
project code, an explicit route-join record for each reusable binding, and a
second normalized ledger before new projects can genuinely relocate. It makes
arbitrary site overrides and implicit tag-driven auto-membership difficult by
design. It does **not** solve transactional host publication, sandboxing,
cross-project scheduling, or migrating embedded absolute paths. Site edits
must change a named join or bind and receive a new provenance/digest, not just
rename a `NN-flow.json` file.

## Architectural checkpoint and review gates

**What becomes possible:** `cfr plan apply/network` and a narrower callable
share one route index; status is one bound action reusable in `apply` and
`status`; project bytes can be selected into a confext without executing the
publication/activation path; a common host runtime can perform truly pre-write
preparation when given controller inputs. **What does not:** confext activation,
safe arbitrary legacy builds, unconditional portability of existing trees, or
bootstrapping the runtime from a not-yet-created project.

Before implementation, review with the operator: (1) whether route-prefix
selection should include a node's own join and all descendants as proposed;
(2) whether phase barriers across network siblings match desired apply order;
(3) whether repeated joins deduplicate only by stable ID; (4) how strict
runtime version pinning and trust of local TS modules should be; (5) whether
new projects should opt into the outward-publication layout immediately; and
(6) directory-only first confext output versus directory+erofs in one builder.
Then take one small observational slice: compile explicit route and asset
records for **static-only**, compare its generated BINS/LINKS with the new
plan, and prove `plan` reads without applying. Only after that implement the
confext build consumer; no installation or network deployment follows from
this design document.
